D-001: Reconnect BoardDistributor to runtime for live/dynamic board food-spawn distribution (replacing DayContentGenerator's pre-authored BoardTimeline replay for everything except Day Start, TriggerStepIndex == -1, which stays authored), with guaranteed-ticket selection made probabilistic (a per-round budget, Poisson-sampled or manually fixed, per-Day configurable; picks tickets via an arrival-order-weighted lottery; any active ticket under a configurable remaining-time threshold, default 10s, is unconditionally guaranteed and consumes from — and may exceed — that budget) — rationale: ExpoTheExplorer/CLAUDE.md Section 3 ("Board / Food Distribution"), still marked Locked, already describes this live required-pool/noise-pool system as current design; it was never updated when an earlier, undocumented change (referred to only in code comments as "PR-6") disconnected BoardDistributor from runtime because a live ticket-lookahead buffer over-consumed the Day's fixed-length pre-authored TicketSequence — fixed here via a non-consuming DayTicketSequenceProvider.PeekUpcoming instead of permanently avoiding a live system; the probabilistic-selection layer (vs. the old deterministic "earliest N") is a new design choice made this session, not a restoration of prior behavior — affects: GameManager.cs, DayTicketSequenceProvider.cs, BoardDistributor.cs, BoardDistributionConfig.cs, DayEditorMetaJson (+ DayEditorModel.cs's editor surface for it), DayContentGenerator.cs, DayEditorBoardTimelinePreview.cs, DaySolvabilityChecker.cs, DayValidator.cs — 2026-08-14

D-002: Remove DaySolvabilityChecker and DayValidator's solvability pre-check entirely (Day Editor's Save-button gate keeps only the ticketSequence.Count == ticketsRequiredForDay check + RetryVariant recursion); delete DayEditorBoardTimelinePreview.cs and DayContentGenerator's per-step board simulation (RegenerateBoardTimeline, EnsureSolvable, and the round-robin delivery/spawn loop inside GenerateCore) — rationale: D-001's live reconnect means "is this Day completable" is now guaranteed BY CONSTRUCTION every OnOrderPlaced call at runtime, not something to pre-validate from a per-step authored schedule; DaySolvabilityChecker's counting math assumed exactly that kind of schedule (a ticket's deadline is satisfied by supply spawned at specific TriggerStepIndex values) and produces nonsensical results once BoardTimeline editing is restricted to Day Start (TriggerStepIndex == -1) only — every demand across the whole Day would need to be pre-supplied at Day Start, permanently failing validation for any real Day. Confirmed with the user (AskUserQuestion, chose "Kaldır") rather than deferring to the roadmap's original Phase 5 slot, since D-001's own Phase 4 (BoardTimeline editing restricted to -1) cannot ship coherently without this — affects: DaySolvabilityChecker.cs (deleted), DayValidator.cs, DayContentGenerator.cs, DayEditorBoardTimelinePreview.cs (deleted), DayEditorModel.cs, DayEditorWindow.cs — 2026-08-14

D-003: Remove the per-Day authored "retry variant" feature entirely — `DayDefinition.RetryVariant` (property + constructor parameter), the `hasRetryVariant`/`retryVariant` JSON sentinel pair on `DayRuntimeJson`, `DayCatalogParser`'s recursive variant resolution, `DayValidator`'s recursive `"RetryVariant: "`-prefixed validation, `DayCatalogNavigator.GetEffectiveDay` (the whole method, its only reason to exist), `GameManager.isRetryAttempt` (so `CurrentDay` is a plain `GetDayAt` again), and the Day Editor's "Retry Variant" foldout together with the `IsTopLevel` flag and `FromDayJson`'s `isTopLevel` parameter that existed solely to support a nested variant model — rationale: requested directly by the user ("projedeki retry variant özelliğinin hepsini kaldırır mısın"); the feature's only ever-realized runtime effect was swapping `TicketsRequiredForDay` on a retry, it carried a `JsonUtility` null-sentinel workaround (roadmap Risk 8) and five levels of empty nested blobs in every authored Day file, and CLAUDE.md Section 4's "difficulty scale-down on life loss" was never answered so nothing shipped depended on it. NOTE: this deletes the mechanism that open question would most naturally have used — a future answer to it starts from scratch rather than from `RetryVariant`. The retry *flow* is untouched: `GameManager.RetryDay()` (free life-loss path) and `RetryCompletedDay()` (voluntary star redo) both still replay the Day itself at unchanged difficulty — affects: DayDefinition.cs, DayJson.cs, DayCatalogParser.cs, DayValidator.cs, DayCatalogNavigator.cs, GameManager.cs, DayEditorModel.cs, DayEditorTicketCardPreview.cs, day_00.json, day_01.json, 7 EditMode suites (DayValidatorTests, DayCatalogNavigatorTests, DayCatalogParserTests, DayEditorModelConverterTests, DayContentGeneratorTests, DayFileIOTests, DayTicketSlotManagerIntegrationTests) — 2026-08-14

D-004: Board-distribution balancing is authored PER DAY in Day JSON (`runtime.boardDistribution`) and is the single runtime authority; `BoardDistributionConfig` is demoted to a Day-Editor seed asset (new-Day starting values + its Inspector preview) and leaves the runtime path entirely. Mechanically: a plain `BoardDistributionSettings` value object in Data replaces the ScriptableObject in `BoardDistributor`'s constructor; `DayCatalogParser` builds it from the Day file and hands it over via `DayDefinition.BoardDistribution`; `GameManager` rebuilds the distributor per Day from `CurrentDay.BoardDistribution` and no longer serializes a config reference; `BoardDistributionConfig.CloneWithOverrides` is deleted — rationale: requested by the user ("bu ayarlar Day Editör kısmında olsun ve bölümün JSON kısmına yazılsın", and explicitly "override kısmını da kaldır çünkü override gibi olmayacak"), so there is no base/override layer — every Day carries a complete block. The per-Day fields already existed but had been placed in `editorMeta`, the one section `DayCatalogParser` is contractually blind to (see the class comment on `DayJson`), so all eight were authored, saved and read by nothing at all; moving them under `runtime` is what makes them real. The plain-settings form (rather than `Instantiate`-ing the asset per Day and overwriting its fields) was chosen because the clone would need explicit `Destroy` on every Day change and retry — one leaked ScriptableObject per transition otherwise — and because CLAUDE.md Section 5 requires the Food Distribution Module to carry no Unity dependency; clamping moved with it into `BoardDistributionSettings`' constructor, which is now the single enforcement point for those bounds. NOTE: this changes gameplay. `BoardDistributionConfig.asset` predates four of the eight fields and reads them at the CLR default, which had silently disabled D-001's urgent-ticket guarantee (`urgentTimeThresholdSeconds` 10 → 0) and flattened its arrival-weighted lottery (`earlyTicketWeightDecay` 0.5 → 0); `day_00`/`day_01` were migrated with the DESIGNED values, not the asset's current ones, after confirming with the user — affects: BoardDistributionSettings.cs (new), BoardDistributionConfig.cs, BoardDistributor.cs, DayJson.cs, DayDefinition.cs, DayCatalogParser.cs, GameManager.cs, DayEditorModel.cs, day_00.json, day_01.json, BoardDistributionTests, BoardDistributionConfigCloneWithOverridesTests (deleted), DayCatalogParserTests, DayEditorModelConverterTests, DayValidatorTests, DayContentGeneratorTests, DayTicketSlotManagerIntegrationTests — 2026-08-17

D-005: The play-time half of `TicketGenerationConfig` — the three patience time limits and `upcomingQueueSize` — is authored per Day in Day JSON (`runtime.ticketRuntime`) and is the single runtime authority for those four values; the generation PROBABILITIES (side/drink inclusion, modification count/direction, main-dish weights) stay where they are, because a Day's `ticketSequence` is rolled at authoring time and baked into the file, so those knobs have already done their work before the Day is ever played. Mechanically: a plain `TicketRuntimeSettings` in Data carries the four values; `TicketRuntimeSettingsExtensions` in Core carries the Impatient/Normal/Patient switch (Data must not reference `Core.PatienceType`, the same constraint `EconomyConfig` already documents), replacing `TicketGenerationConfigExtensions`, which is deleted; `DayCatalogParser` resolves the block onto `DayDefinition.TicketRuntime`; `TicketEntryFactory` and `DayTicketSequenceProvider` take the settings instead of the config asset; `GameManager` reads the lookahead from `CurrentDay.TicketRuntime`. `TicketGenerationConfig` survives — unlike `BoardDistributionConfig` in D-004 — because it still owns the names database (a TextAsset reference that cannot live in Day JSON) and the generation knobs, and it gains `ToRuntimeSettings()` as the authoring-side seed. NOTE: the plan called for making `TicketFactory` per-Day as well; reading the code showed that is unnecessary — at play time `TicketFactory` is only a customer-name picker (`Create`/`PickRandomPatienceType` are authoring-only), and the name pool is not per-Day balancing, so it stays session-scoped. Unlike D-004 this changes no behaviour: `TicketGenerationConfig.asset` carried all four values (45/90/150/10) and both Days were migrated with exactly those — affects: TicketRuntimeSettings.cs (new), TicketRuntimeSettingsExtensions.cs (new), TicketGenerationConfigExtensions.cs (deleted), TicketGenerationConfig.cs, TicketFactory.cs, DayJson.cs, DayDefinition.cs, DayCatalogParser.cs, DayTicketSequenceProvider.cs, TicketEntryFactory.cs, GameManager.cs, DayEditorModel.cs, day_00.json, day_01.json, TicketRuntimeSettingsExtensionsTests (new), TicketGenerationConfigExtensionsTests (deleted), TicketEntryFactoryTests, DayTicketSequenceProviderTests, DayCatalogParserTests, DayEditorModelConverterTests, DayTicketSlotManagerIntegrationTests, DayValidatorTests, DayContentGeneratorTests — 2026-08-17

D-006: The ticket-GENERATION settings (side/drink inclusion chance, fallback modification-count lambda, modification-addition chance, main-dish weights) are authored per Day as a complete block in `editorMeta.ticketGeneration`, with no override layer: the `hasTicketGenerationOverride` toggle and the `...Override` field suffixes are gone, and `TicketGenerationConfig.CloneWithOverrides` (nullable params, inherit-what-you-omit) becomes `CloneForDayGeneration` (all five required). `modificationAdditionChance` and `mainDishWeights` were previously not per-Day at all and are added, so the record is complete; weights are stored as food ids and resolved via `FoodCatalog` (`DayContentGenerator.ResolveMainDishWeights`), dropping ids whose `FoodItemConfig` is gone, the same stance `ResolveFoodPool` takes. `MainDishWeight` gains a public constructor so a Day's resolved weights can be built in code — rationale: the user's stated reason for keeping these in the Day file is being able to return to a Day later, SEE which settings it was generated with, and re-generate from them; a partial record ("hangi ayarla yapılmış" minus two of the knobs) would not serve that. These stay in `editorMeta` rather than moving under `runtime` — unlike D-004/D-005 — because a Day's `ticketSequence` is rolled at authoring time and baked into the file, so the probabilities have already done their work before the Day is ever played; `DayCatalogParser`'s contract of never reading `editorMeta` is therefore preserved, and `ParseAll_EditorMetaFieldsIgnored_DoesNotAffectResolution` still enforces it. Deliberate asymmetry with D-004/D-005: a missing block here is NOT fatal (the runtime blocks drop the Day; this one falls back to the seed asset's real values and is written out on the next Save), because runtime correctness does not depend on it and an old Day must stay openable. The Instantiate-clone is also kept here, unlike D-004, because `TicketFactory` needs `namesDatabase` — a TextAsset reference that cannot live in Day JSON — and this path runs only at authoring time and destroys the clone in a `finally`, so there is no per-Day runtime lifetime to leak. No behaviour change: both Days were migrated with the asset's exact values (0.9 / 0.9 / 1.69 / 0.5 / burger weight 1 lambda 2; the weight entry's GUID resolved to Food_Burger, which both Days already serve) — affects: TicketGenerationConfig.cs, DayJson.cs, DayContentGenerator.cs, DayEditorModel.cs, day_00.json, day_01.json, TicketGenerationConfigCloneForDayGenerationTests (replaces TicketGenerationConfigCloneWithOverridesTests), DayContentGeneratorTests, DayCatalogParserTests, DayEditorModelConverterTests — 2026-08-17

D-007: Delete `BoardDistributionConfig` outright — the ScriptableObject class, its `.asset`, and `BoardDistributionConfigEditor` — and seed a new Day's board-distribution balancing from the highest-numbered existing Day instead. `GuaranteedTicketCountMode` moves to `BoardDistributionSettings.cs` (same namespace, so nothing that uses the enum changed), and the leak-distribution preview that only that custom editor drew moves into `DayEditorSettingsPreviews`, shared with the Day Editor and with `TicketGenerationConfigEditor`'s main-dish preview — rationale: after D-004 took the asset off the runtime path its only remaining consumer was its own inspector preview, i.e. a preview of numbers that no longer drove anything; the user asked for it to go ("SOlara gerek kalmadıysa silsek ya"). Seeding from the previous Day (user's choice among three options, 2026-08-17) keeps the numbers in DATA rather than in code, which the root CLAUDE.md invariant requires and which a coded default would have quietly broken — the coded defaults on `DayEditorBoardDistribution` now only apply to the very first Day of an empty catalog. It also matches how Days are actually authored: the next Day usually starts from the last one's balance. Only the three balancing blocks are copied; ticket sequence, Day Start board, star thresholds and food selection are not, since those are what distinguishes one Day from another and inheriting them would disguise an empty new Day as a finished one. `TicketGenerationConfig` survives this deletion for the reasons in D-006 (it owns `namesDatabase` and the generation knobs) and still seeds a new Day's generation/runtime blocks. NOTE: `SampleScene.unity` still carries a `boardDistributionConfig:` line (line 3003) left from the field removed in D-004; with the asset gone it is a dangling GUID on a property no class declares, which Unity drops the next time the scene is saved. The scene was deliberately not hand-edited: it is the project's only scene and K1, and one line of cosmetic cleanup does not justify editing serialized YAML by hand — affects: BoardDistributionConfig.cs (deleted), BoardDistributionConfig.asset (deleted), BoardDistributionConfigEditor.cs (deleted), BoardDistributionSettings.cs, DayEditorSettingsPreviews.cs (new), DayEditorModel.cs, DayEditorWindow.cs, TicketGenerationConfigEditor.cs, SampleScene.unity (stale reference, left for Unity to drop) — 2026-08-17

D-008: The Day Complete popup's 3-star rating is computed from lives lost that day -- 0 lost = 3 stars, 1 = 2, 2 = 1, 3 or more = 0 -- instead of comparing the day's earned score against per-Day authored thresholds. `startingLives` drops from 5 to 3 so the mapping covers the whole reachable range without a gap, the rule moves out of `DayCompletePopupView` into `DayLifecycleManager.StarCount` (which already owns the failure counter, and where it can be tested), and `star1Threshold`/`star2Threshold`/`star3Threshold` are deleted from Day JSON, `DayDefinition`, `GameManager`, the Day Editor and `DayValidator` along with the two warnings about them -- rationale: requested by the user ("elle ayarlamak yerine..."), and the thresholds were a per-Day balancing chore that nobody had actually done: both shipped Days sat at 0/0/0, which awarded 3 stars for any result at all. Lives-based rating needs no authoring per Day and scales with whatever difficulty a Day happens to have. NOTE this changes a rule CLAUDE.md marked as locked, on the user's decision, and it has two consequences worth keeping visible: (1) stars now measure accuracy alone -- speed and patience multipliers still drive the money earned but no longer affect the rating, so there is no star incentive to play fast; (2) 3 starting lives instead of 5 is a real difficulty increase, chosen deliberately over leaving a 3-and-4-losses gap in the mapping. The 3+ case is only reachable through a paid continue (which refills lives but deliberately leaves the failure counter alone) and floors at 0 stars: the day still completes and still pays out, it just earns nothing to show. The GDD .docx is not updated here -- binary file, left to the user -- affects: DayLifecycleManager.cs, DayCompletePopupView.cs, GameManager.cs, DayJson.cs, DayDefinition.cs, DayCatalogParser.cs, DayValidator.cs, DayEditorModel.cs, GameConfig.asset, day_00.json, day_01.json, DayLifecycleManagerTests, DayValidatorTests, DayEditorModelConverterTests, ExpoTheExplorer/CLAUDE.md — 2026-08-17

D-009: Remove the player XP / Level system from the game entirely — `LevelManager` (XP calculation, level-up loop, commit/discard/revert of progress), `LevelProgressionConfig` + its `.asset` (XP-per-item, the three patience XP multipliers, the `XpToNextLevel` threshold table), `GameState.Xp`/`GameState.Level` with their `XpChanged`/`LevelChanged` event buses and constructor seeds, the `XpBarView` and `LevelView` HUD components together with the whole `LevelUI` GameObject subtree in `SampleScene` (level badge, XP bar background/fill/frame, level count text — 6 GameObjects, 24 YAML blocks), `GameManager`'s XP wiring (the `levelProgressionConfig` serialized field, the profile load in `Awake`, the XP award in `OnTicketDelivered`, the `OnDayCompleted`/`OnDayRetried` handlers and their subscriptions, and the `dayStartProfile` half of `CaptureDayStartSnapshot`), and `ProgressionSystemTests` — rationale: requested directly by the user ("XP sistemine dair her şeyi siler misin, Level sistemi olmayacak artık oyunda"). Three consequences worth keeping visible: (1) **patience is now a one-effect stat** — the XP multiplier was its second effect, so patience type feeds nothing but the ticket's time limit, which sharpens GDD open question 22 rather than closing it; (2) **the game persists nothing at all** — Xp/Level was the only state ever written to disk, so every session now starts from `GameState`'s constructor, Day 0 included; (3) the powerup design's "granted on level-up" earn path is void, and powerups (already deferred) will need a new trigger if that scope reopens. `PlayerProfile`/`PlayerProfileStore` and the `ProgressionSystem` assembly are deliberately KEPT rather than deleted with the rest: they are the save *boundary*, not XP-specific, and two queued tasks land in exactly that file — persisting `CurrentDayIndex` (DaySystem_Roadmap Q4) and the wallet plus a schema version (`economy-plan.md` Adım 2). `PlayerProfile` is therefore an empty `[Serializable]` class today and `PlayerProfileStore` has no caller; `PlayerProfileStoreTests` was re-pointed from payload assertions to file behavior (missing/empty/corrupt/round-trip/directory creation, with fallback identity via `AreSame`) so that coverage survives the empty payload. Two `GameStateTests` cases that happened to sit on Xp/Level were re-pointed at SoftMoney rather than deleted — what they guard is the publish-only-on-change setter pattern shared by every reactive `GameState` field. An existing `player_profile.json` in `persistentDataPath` is simply never read again; no migration was written for it — affects: GameState.cs, GameManager.cs, DayCompletePopupView.cs, PlayerProfile.cs, PlayerProfileStore.cs, LevelManager.cs (deleted), LevelProgressionConfig.cs + .asset (deleted), LevelView.cs (deleted), XpBarView.cs (deleted), SampleScene.unity, ProgressionSystemTests (deleted), PlayerProfileStoreTests, GameStateTests, ExpoTheExplorer/CLAUDE.md, GDD (v1.0), docs/LevelSystem_Roadmap.md (deleted), docs/DaySystem_Roadmap.md, blueprint.md, fingerprint.md, economy-plan.md, day-config-plan.md — 2026-08-18
