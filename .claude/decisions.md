D-001: Reconnect BoardDistributor to runtime for live/dynamic board food-spawn distribution (replacing DayContentGenerator's pre-authored BoardTimeline replay for everything except Day Start, TriggerStepIndex == -1, which stays authored), with guaranteed-ticket selection made probabilistic (a per-round budget, Poisson-sampled or manually fixed, per-Day configurable; picks tickets via an arrival-order-weighted lottery; any active ticket under a configurable remaining-time threshold, default 10s, is unconditionally guaranteed and consumes from — and may exceed — that budget) — rationale: ExpoTheExplorer/CLAUDE.md Section 3 ("Board / Food Distribution"), still marked Locked, already describes this live required-pool/noise-pool system as current design; it was never updated when an earlier, undocumented change (referred to only in code comments as "PR-6") disconnected BoardDistributor from runtime because a live ticket-lookahead buffer over-consumed the Day's fixed-length pre-authored TicketSequence — fixed here via a non-consuming DayTicketSequenceProvider.PeekUpcoming instead of permanently avoiding a live system; the probabilistic-selection layer (vs. the old deterministic "earliest N") is a new design choice made this session, not a restoration of prior behavior — affects: GameManager.cs, DayTicketSequenceProvider.cs, BoardDistributor.cs, BoardDistributionConfig.cs, DayEditorMetaJson (+ DayEditorModel.cs's editor surface for it), DayContentGenerator.cs, DayEditorBoardTimelinePreview.cs, DaySolvabilityChecker.cs, DayValidator.cs — 2026-08-14

D-002: Remove DaySolvabilityChecker and DayValidator's solvability pre-check entirely (Day Editor's Save-button gate keeps only the ticketSequence.Count == ticketsRequiredForDay check + RetryVariant recursion); delete DayEditorBoardTimelinePreview.cs and DayContentGenerator's per-step board simulation (RegenerateBoardTimeline, EnsureSolvable, and the round-robin delivery/spawn loop inside GenerateCore) — rationale: D-001's live reconnect means "is this Day completable" is now guaranteed BY CONSTRUCTION every OnOrderPlaced call at runtime, not something to pre-validate from a per-step authored schedule; DaySolvabilityChecker's counting math assumed exactly that kind of schedule (a ticket's deadline is satisfied by supply spawned at specific TriggerStepIndex values) and produces nonsensical results once BoardTimeline editing is restricted to Day Start (TriggerStepIndex == -1) only — every demand across the whole Day would need to be pre-supplied at Day Start, permanently failing validation for any real Day. Confirmed with the user (AskUserQuestion, chose "Kaldır") rather than deferring to the roadmap's original Phase 5 slot, since D-001's own Phase 4 (BoardTimeline editing restricted to -1) cannot ship coherently without this — affects: DaySolvabilityChecker.cs (deleted), DayValidator.cs, DayContentGenerator.cs, DayEditorBoardTimelinePreview.cs (deleted), DayEditorModel.cs, DayEditorWindow.cs — 2026-08-14

D-003: Remove the per-Day authored "retry variant" feature entirely — `DayDefinition.RetryVariant` (property + constructor parameter), the `hasRetryVariant`/`retryVariant` JSON sentinel pair on `DayRuntimeJson`, `DayCatalogParser`'s recursive variant resolution, `DayValidator`'s recursive `"RetryVariant: "`-prefixed validation, `DayCatalogNavigator.GetEffectiveDay` (the whole method, its only reason to exist), `GameManager.isRetryAttempt` (so `CurrentDay` is a plain `GetDayAt` again), and the Day Editor's "Retry Variant" foldout together with the `IsTopLevel` flag and `FromDayJson`'s `isTopLevel` parameter that existed solely to support a nested variant model — rationale: requested directly by the user ("projedeki retry variant özelliğinin hepsini kaldırır mısın"); the feature's only ever-realized runtime effect was swapping `TicketsRequiredForDay` on a retry, it carried a `JsonUtility` null-sentinel workaround (roadmap Risk 8) and five levels of empty nested blobs in every authored Day file, and CLAUDE.md Section 4's "difficulty scale-down on life loss" was never answered so nothing shipped depended on it. NOTE: this deletes the mechanism that open question would most naturally have used — a future answer to it starts from scratch rather than from `RetryVariant`. D-004: Board-distribution balancing is authored PER DAY in Day JSON (`runtime.boardDistribution`) and is the single runtime authority; `BoardDistributionConfig` is demoted to a Day-Editor seed asset (new-Day starting values + its Inspector preview) and leaves the runtime path entirely. Mechanically: a plain `BoardDistributionSettings` value object in Data replaces the ScriptableObject in `BoardDistributor`'s constructor; `DayCatalogParser` builds it from the Day file and hands it over via `DayDefinition.BoardDistribution`; `GameManager` rebuilds the distributor per Day from `CurrentDay.BoardDistribution` and no longer serializes a config reference; `BoardDistributionConfig.CloneWithOverrides` is deleted — rationale: requested by the user ("bu ayarlar Day Editör kısmında olsun ve bölümün JSON kısmına yazılsın", and explicitly "override kısmını da kaldır çünkü override gibi olmayacak"), so there is no base/override layer — every Day carries a complete block. The per-Day fields already existed but had been placed in `editorMeta`, the one section `DayCatalogParser` is contractually blind to (see the class comment on `DayJson`), so all eight were authored, saved and read by nothing at all; moving them under `runtime` is what makes them real. D-008: The Day Complete popup's 3-star rating is computed from lives lost that day -- 0 lost = 3 stars, 1 = 2, 2 = 1, 3 or more = 0 -- instead of comparing the day's earned score against per-Day authored thresholds. `startingLives` drops from 5 to 3 so the mapping covers the whole reachable range without a gap, the rule moves out of `DayCompletePopupView` into `DayLifecycleManager.StarCount` (which already owns the failure counter, and where it can be tested), and `star1Threshold`/`star2Threshold`/`star3Threshold` are deleted from Day JSON, `DayDefinition`, `GameManager`, the Day Editor and `DayValidator` along with the two warnings about them -- rationale: requested by the user ("elle ayarlamak yerine..."), and the thresholds were a per-Day balancing chore that nobody had actually done: both shipped Days sat at 0/0/0, which awarded 3 stars for any result at all. Lives-based rating needs no authoring per Day and scales with whatever difficulty a Day happens to have. NOTE this changes a rule CLAUDE.md marked as locked, on the user's decision, and it has two consequences worth keeping visible: (1) stars now measure accuracy alone -- speed and patience multipliers still drive the money earned but no longer affect the rating, so there is no star incentive to play fast; (2) 3 starting lives instead of 5 is a real difficulty increase, chosen deliberately over leaving a 3-and-4-losses gap in the mapping. The 3+ case is only reachable through a paid continue (which refills lives but deliberately leaves the failure counter alone) and floors at 0 stars: the day still completes and still pays out, it just earns nothing to show. The GDD .docx is not updated here -- binary file, left to the user -- affects: DayLifecycleManager.cs, DayCompletePopupView.cs, GameManager.cs, DayJson.cs, DayDefinition.cs, DayCatalogParser.cs, DayValidator.cs, DayEditorModel.cs, GameConfig.asset, day_00.json, day_01.json, DayLifecycleManagerTests, DayValidatorTests, DayEditorModelConverterTests, ExpoTheExplorer/CLAUDE.md — 2026-08-17

D-009: Remove the player XP / Level system from the game entirely — `LevelManager` (XP calculation, level-up loop, commit/discard/revert of progress), `LevelProgressionConfig` + its `.asset` (XP-per-item, the three patience XP multipliers, the `XpToNextLevel` threshold table), `GameState.Xp`/`GameState.Level` with their `XpChanged`/`LevelChanged` event buses and constructor seeds, the `XpBarView` and `LevelView` HUD components together with the whole `LevelUI` GameObject subtree in `SampleScene` (level badge, XP bar background/fill/frame, level count text — 6 GameObjects, 24 YAML blocks), `GameManager`'s XP wiring (the `levelProgressionConfig` serialized field, the profile load in `Awake`, the XP award in `OnTicketDelivered`, the `OnDayCompleted`/`OnDayRetried` handlers and their subscriptions, and the `dayStartProfile` half of `CaptureDayStartSnapshot`), and `ProgressionSystemTests` — rationale: requested directly by the user ("XP sistemine dair her şeyi siler misin, Level sistemi olmayacak artık oyunda"). Three consequences worth keeping visible: (1) **patience is now a one-effect stat** — the XP multiplier was its second effect, so patience type feeds nothing but the ticket's time limit, which sharpens GDD open question 22 rather than closing it; (2) **the game persists nothing at all** — Xp/Level was the only state ever written to disk, so every session now starts from `GameState`'s constructor, Day 0 included; (3) the powerup design's "granted on level-up" earn path is void, and powerups (already deferred) will need a new trigger if that scope reopens. `PlayerProfile`/`PlayerProfileStore` and the `ProgressionSystem` assembly are deliberately KEPT rather than deleted with the rest: they are the save *boundary*, not XP-specific, and two queued tasks land in exactly that file — persisting `CurrentDayIndex` (DaySystem_Roadmap Q4) and the wallet plus a schema version (`economy-plan.md` Adım 2). `PlayerProfile` is therefore an empty `[Serializable]` class today and `PlayerProfileStore` has no caller; `PlayerProfileStoreTests` was re-pointed from payload assertions to file behavior (missing/empty/corrupt/round-trip/directory creation, with fallback identity via `AreSame`) so that coverage survives the empty payload. Two `GameStateTests` cases that happened to sit on Xp/Level were re-pointed at SoftMoney rather than deleted — what they guard is the publish-only-on-change setter pattern shared by every reactive `GameState` field. D-010: SoftMoney and Gems get a single, compiler-enforced writer, a day attempt becomes economically atomic, and the wallet becomes the only persisted state. Mechanically: a new `Wallet` in ProgressionSystem owns every balance change (`EarnSoftMoney`, `TrySpendSoftMoney`, `TrySpendGems`, `CaptureDayStart`, `RevertToDayStart`, `ApplyPersistedBalances`); `GameState`'s two balance setters drop from public to `internal` and a new `Core/AssemblyInfo.cs` names ProgressionSystem (plus `Tests.EditMode`) as the only friend assemblies, so Bootstrap, LivesSystem and UI cannot assign a balance at all -- `State.SoftMoney = x` outside those two is a build error. `Wallet` keeps a day-start snapshot of both currencies and a per-day spend ledger; `RevertToDayStart` applies `max(0, dayStartBalance - spentThisDay)` to both. `PlayerProfile` gains `Version` + `SoftMoney` + `Gems`, `PlayerProfileStore` owns `CurrentVersion = 1`, stamps it on every Save, decides the file location itself (`persistentDataPath/player_profile.json`, keeping System.IO out of Bootstrap) and on Load accepts versions 1..CurrentVersion while refusing 0 and anything newer. `GameManager` loses its own `dayStartSoftMoney` field and `CaptureDayStartSnapshot`, gains a `PlayerProfileStore`, and re-creates the `OnDayRetried` and `OnDayCompleted` handlers plus their subscriptions -- both had been deleted by D-009 along with the XP discard/commit they also performed — rationale: three separate audit findings shared one root cause, that nothing owned the currencies. SoftMoney had four writers (GameManager's payout and its RetryCompletedDay rollback, LivesManager's two paid Continues), violating the root CLAUDE.md single-writer invariant; a failed day KEPT the money it had earned, so deliberately losing a day was a way to farm income; and `RetryCompletedDay` handed back a paid Continue. The atomic-day contract ("a day's economic result is provisional until the day completes: earnings are taken back, spending is never refunded") closes the second and third at once and is the same shape the removed XP system already had. The `max(0, ...)` clamp is the user's decision D1, chosen over the alternative of barring Continue purchases funded by the current day's earnings -- one fewer rule for the player, at the cost that a player who funds a Continue that way can end a failed day poorer than they started it, though never in debt. The version-range check is deliberately NOT the plan's "reject anything != 1": that would delete a real player's v1 wallet the day a v2 field is added, whereas an older file is readable and simply lacks the newer fields; version 0 stays refused because an unversioned file's numbers could mean anything and are indistinguishable from a genuine 0 balance, which is the entire reason the invariant demands a version field. NOTE the ledger and snapshots reset only in `CaptureDayStart` (day start / day advance), never on a retry, so two Continues bought across two failed attempts of one day are both still spent and both measured against that day's single baseline. NOTE also `CurrentDayIndex` is deliberately NOT persisted (DaySystem_Roadmap Q4 is a gameplay decision left to the user); the versioned schema makes adding it later cheap, since an existing file reads the missing field as 0, which is exactly "start at Day 0". Only two places write to disk -- `DayCompleted` and `RetryCompletedDay`, the latter because it must correct a figure a completed day already banked -- so quitting mid-day loses that day's earnings by design — affects: Wallet.cs (new), AssemblyInfo.cs (new), WalletTests.cs (new), GameState.cs, PlayerProfile.cs, PlayerProfileStore.cs, LivesManager.cs, ExpoTheExplorer.Systems.LivesSystem.asmdef (+ProgressionSystem reference, new one-directional arrow LivesSystem -> ProgressionSystem), GameManager.cs, LivesSystemTests.cs, PlayerProfileStoreTests.cs, blueprint.md, fingerprint.md, ExpoTheExplorer/CLAUDE.md — 2026-08-18

D-011: A delivery's payout is the summed base prices of the ticket's food (fixed, always paid in full) plus a tip that is a percentage of that same order value, and the tip percentage steps down through three tiers keyed to the fraction of the ticket's OWN time limit still left. The 3-tier speed bonus (Lightning/Fast/Standard, its three multipliers and its two seconds-per-item thresholds) and the entire patience tip-decay machinery (`PatienceDecayStep`, the three authored curves, `ResolvePatienceDecayCoefficient`) are DELETED, not deferred. Mechanically: `FoodItemConfig` gains an authored `basePrice`; `EconomyCalculator.CalculateTip` becomes `CalculatePayout` returning `DeliveryPayoutResult` (`OrderValue`/`Tier`/`TipRate`/`Tip`/`Total`) with a new `TipTier` enum; `EconomyConfig` drops `baseTipPerItem` and the speed knobs and gains `tipRateFull`/`tipRateWarning`/`tipRateCritical` plus `warningRatio`/`criticalRatio`; the two ratios MOVE out of `TicketCardVisualsConfig` (which keeps only the three bar colours and the purely cosmetic `timerSegmentSeconds`) so that one authored value drives both the timer bar's colour and the tip tier, with `TicketCardsView` reading them through a new `GameManager.EconomyConfig` getter; `DayLifecycleManager` renames its private fields but keeps its public property names so `DayCompletePopupView` needed no change; `EconomyConfigEditor` was first rewritten as a tier preview and then deleted at the user's request — rationale: requested by the user across several turns. Item count no longer decides what a delivery is worth (a burger, fries and a cola are not interchangeable), which is what `baseTipPerItem` implied. The old speed tiers were removed even though the GDD marked them locked, because their thresholds were computed as seconds-per-item and were therefore invisible on screen, while the timer bar with its colour changes is already on the card -- of two mechanics doing the same job, the visible one was kept. Keying the tiers to a RATIO rather than seconds makes them scale per patience type for free: an Impatient 45s ticket drops a tier every 15s, a Patient 150s one every 50s, which is now the concrete mechanism behind "patience affects money only through the time limit it grants". Putting the ratios on `EconomyConfig` was the user's explicit instruction, twice confirmed; the visuals copy was deleted rather than kept alongside so the colour the player sees and the tip they are paid cannot drift apart, and the Day Editor's card preview turned out not to read those ratios at all, so no editor work was needed. Order value is never scaled by anything, so a late delivery loses tip but never the food's price -- which also means the Day Complete popup's "Tips" row can no longer go negative, a bug the old `TotalTip - BaseTip` subtraction produced whenever a patience coefficient below 1 pulled the total under its own base. NOTE this changes balance: with the authored 20/10/5 rates the spread between a perfect and a last-second delivery on a 21-value order is 25 vs 22, so speed is currently a minor income factor. NOTE also the deleted `EconomyConfigEditor` had warned about two authoring mistakes nothing now checks -- ratios authored so the Warning tier is unreachable, and rates ordered so a LATER delivery pays more — affects: FoodItemConfig.cs, EconomyConfig.cs, EconomyCalculator.cs, TicketCardVisualsConfig.cs, TicketCardsView.cs, GameManager.cs, DayLifecycleManager.cs, EconomyConfigEditor.cs (deleted), EconomySystemTests.cs, DayLifecycleManagerTests.cs, DayTicketSlotManagerIntegrationTests.cs, TicketSystemTests.cs, the nine Food_*.asset price fields, blueprint.md (new arrow TicketSystem -> EconomySystem), fingerprint.md, ExpoTheExplorer/CLAUDE.md, docs/Expo_the_Explorer_GDD_1.md (v0.8 → v1.1) — 2026-08-18

D-012: The game gets a second scene, `MainScreen`, and the day scene gets three working exits to it; `CurrentDayIndex` becomes persisted (profile schema v1 → v2), which closes DaySystem_Roadmap Q4. Mechanically: a new `SceneFlow` in Core holds the two scene names and the two Single-mode loads; `MainScreenView` (Scripts/UI) renders the day number and both balances read straight from `PlayerProfileStore.Load()` and sends the player back into the day; `PlayerProfile` gains `CurrentDayIndex` and `PlayerProfileStore.CurrentVersion` goes to 2; `GameManager` applies the persisted index in `Awake` through a new `ResolveStartingDayIndex` clamp (after the catalog is parsed, before the provider is built off `CurrentDay`), writes it in `SaveProfile`, and gains `ReturnToMainScreenFromCompletedDay` + `ReturnToMainScreenAbandoningDay`; `DayCompletePopupView.goBackButton` and `GameOverPopupView.mainMenuButton` lose their `interactable = false` lines and get listeners; `AdvanceToNextDay` now also saves. The scene itself is produced by a construction script, `MainScreenSceneBuilder` — rationale: requested by the user ("bölüm bitince ana ekrana gidebilmeliyim"), and both buttons had been sitting in `SampleScene` since their popups were built, disabled behind a `// TODO: wire once a menu/day-select scene exists`. Scope was confirmed with the user before any code: a navigation shell (not a day-select map, not a hub with upgrades — no meta CONTENT is designed here, only the flow it will hang off), resume-where-you-left-off, and a separate scene rather than an in-scene panel. **Separate Single-mode scenes** matter beyond taste: the day scene is destroyed on exit, so `GameManager` keeps its "Awake builds the whole Day" shape and its ~dozens of hand-wired Inspector references untouched, and no day runtime lives on behind the main screen. With no persistent scene, **the save file is the hand-off between the two scenes**, which is why `MainScreenView` reads the profile directly — it is a pure reader, so `GameManager` remains the single writer of both balances and the day index. Three sub-decisions worth keeping visible: (1) **"Go Back" advances the day.** The day is finished when that button is reachable, so the next thing the main screen should offer is the next Day. It deliberately does NOT call `AdvanceToNextDay`: only the index has to survive, and that method's board/tray/slot reset would be thrown away as the scene unloads while cascading `TicketAssigned` through views that are already tearing down. (2) **Leaving a failed attempt now WRITES to disk** — `Wallet.RevertToDayStart()` then `SaveProfile()` — which changes the older "a failed day never writes" line in this file's D-010 and in CLAUDE.md. It has to: the new button creates a hole that did not exist while there was nowhere to go, since without the write a Continue bought with **Gems** during an attempt the player then abandons would be silently refunded by walking out, making paid Continues free for anyone who ends up leaving. The write can only ever record money already SPENT, never earned, so it cannot bank a failed day's income — the atomic-day contract is extended to "leaving settles the attempt the way a retry does", not reversed. The day index is deliberately not advanced there, so the main screen still offers that same Day. (3) **The last authored Day gets an answer**: "Next Day" used to return false and just hide the popup, leaving the player on a finished day with no UI at all (the code called this "PR-9 decides"); it now exits to the main screen, whose Play replays that last Day since the index cannot advance. A real "all days finished" screen is content, deliberately not invented here. NOTE the scene is built by an Editor construction script rather than committed as YAML: a Canvas+TMP scene hand-written as serialized YAML is exactly the edit D-007 declined to make, it cannot be reviewed, and a scene file cannot put itself first in Build Settings. D-015: The meta side of the game — the expo grounds the player decorates between days — gets a designed shape and a new `MetaSystem`, built MULTI-LOCATION from the first line. This is the project's first DESIGN-ONLY decision record: no code ships with it, because ExpoTheExplorer/CLAUDE.md's "Meta content … is not designed yet — build the design first, then hang it here" makes the design itself the deliverable, and `.claude/meta-plan.md` is its 11-step execution plan. Six mechanisms, each with the alternative it beat. (1) **One slot = one Image with two sprites.** A catalog entry carries `unownedSprite` and `ownedSprite`, either of which may be empty, so the whole view layer is `image.sprite = active ? owned : unowned; image.enabled = image.sprite != null`. This collapses what looked like four product types into one code path: a cosmetic decor has only an owned sprite; the ruined `StartBuilding` that hides the finished stand has only an UNOWNED one and therefore vanishes when bought; an area expansion (`Square`) is a decor that additionally unlocks slots; a Day-unlocked prop differs only in what decides `active`. The rejected alternative was a `kind` enum with a switch per type — four branches to keep in sync for a two-field data change. (2) **A Day-unlocked prop's openness is DERIVED, never persisted**: `active ⟺ some Day in 0..CurrentDayIndex serves the trigger content`. Because `CurrentDayIndex` names the day about to be played, that scan opens the prop exactly BEFORE the day that needs it, which is what the user asked for ("sonraki bölümde sos vardır, o bölümden önce açılması gerekir") and it needs no `+1`. Persisting the unlocked set was rejected outright: it is a second authority that starts lying the moment a Day is re-authored. The trigger is `DayUnlockTrigger` with four optional fields OR-ed together — `foods` (FoodItemConfig refs), `foodCategories` (FoodCategory), `modifications` (ModificationConfig refs) and a plain `minDayIndex` — because the three props Meta1 actually has each look at a DIFFERENT concept: the fryer at one food (`Food_Fries`), the drinks fridge at a whole category (six beverages, so a seventh added later cannot silently fail to trigger it), and the sauces stand at a set of modifications (`Mod_ExtraKetchup`/`Mayonnaise`/`Mustard` — note `FoodCategory` has no `Sauce` member; sauces are modifications, which is why one trigger shape could not serve all three). Everything is an ASSET REFERENCE, not a string id, so the root invariant on content-never-in-code holds and renames cannot break it. (3) **The wallet keeps its single writer on the main screen, via a `GameSession` extracted from `GameManager` rather than a second construction path.** A shop that spends money needs a `Wallet`, and the main screen has neither `GameManager` nor `GameState` by design (D-012/D-013). `GameManager.Awake`'s first five steps — `GameState`, `Wallet` + `ApplyPersistedBalances`, `LivesManager` + `ApplyPersistedLives`, the Day catalog parse, and the `ResolveStartingDayIndex` clamp — are exactly what the meta screen needs and exactly one contiguous block, so they become `GameSession` and BOTH screens construct it. Writing a separate `MetaScreenController` that re-implemented those five was designed and REJECTED: four load-bearing ordering rules live in that block (the wallet must exist before `ApplyPersistedBalances` because GameState's setters are `internal`; `LivesManager` before anything that can cost a life; the catalog before the clamp, which needs its `Count`; and `ApplyPersistedBalances` re-takes the day-start snapshot), and duplicating them across two files is the exact failure the single-writer invariant exists to prevent. Moving `GameManager` itself to the main screen — the user's question — was rejected for a concrete reason: `Awake` ends in `ApplyDayStartBoardPreSeed()` + `TicketSlotManager.FillEmptySlots()` and `Update()` runs `TicketSlotManager.Tick`, so the day would RUN behind the shop, timing tickets out and costing lives; a `DontDestroyOnLoad` variant fails differently, since every view in `SampleScene` holds a `[SerializeField] GameManager` that a carried-in object cannot satisfy, which would reverse the user's explicit D-013 instruction. `GameSession` being plain C# in an asmdef also closes a coverage gap D-012 recorded: `ResolveStartingDayIndex`'s clamp becomes EditMode-testable for the first time. Alongside it, `player_profile.json` gets ONE writer class (`ProfileSaver`) that both `GameManager` and the meta screen call with a whole profile, so the file cannot be written with a stale day index or lives; and `HudWalletSource` binds to a `GameSession` provider instead of a concrete `GameManager`, which makes the main-screen HUD live after a purchase and follows D-013/D-014's own rule to extend the source rather than branch inside a view. (4) **No third scene**: the grounds render inside `MainScreen`, which the GDD already designated ("hang it here") and which leaves D-012's two-scene shape untouched — a third scene would add a second save-file hand-off. (5) **Slot positions are normalized (0..1) to the background rect**, not pixels: `Main.png` is 853×1844 (0.463, a phone portrait ratio) but real devices run 0.42–0.56, so pixel offsets drift under aspect-fill while normalized ones do not — and it lets locations with differently-sized backgrounds share one data shape. 19 slots are too many to hand-author, so an Editor placement tool writes positions back into the asset, the same authoring-tool pattern DayEditor and MainScreenSceneBuilder already use. (6) **Location is a first-class entity and decor belongs to it** (`MetaCatalog.locations` → `MetaLocation{ id, displayName, backgroundSprite, unlockAtDayIndex, items[] }`), because the user stated a second restaurant is coming and that which props are cosmetic vs. Day-unlocked "metadan metaya değişebilir". Consequences: the persistence key is `$"{location.Id}.{item.Id}"` COMPUTED by the resolver, so assets keep clean local ids while uniqueness is structural and two locations can carry a same-named decor; a location's unlock is derived from `CurrentDayIndex >= unlockAtDayIndex`, the same shape as (2), so no save field; the wallet is SHARED across locations while decor is not; which location is being viewed is UI state, not saved (the screen opens on the newest unlocked one); and a location is self-contained — a `requiresAreaId` pointing into another location is a validation error. Doing this now costs a wrapper level in the catalog and a location parameter on the resolver; doing it later would have meant changing the schema of already-saved ownership keys, i.e. a save migration. Deliberately NOT built: any gameplay effect (decor is purely cosmetic — no income multiplier, no lives), Gems anywhere on the meta side (they stay Continue-only), free placement (fixed slots, the user's choice), a day-select map, per-location economies, and decor transferable between locations. Two design consequences worth keeping visible: a Day-unlocked prop's trigger reads GLOBAL content rather than a location's own timeline, so a location unlocking at Day 12 opens with its fridge already present if drinks entered at Day 3 (correct — the new restaurant is built with everything already on the menu); and the "old location stays visitable and decorable" rule is what removes the sunk-cost trap that a hard move would have created, where every coin spent before the move stops being visible and the rational player therefore ignores the meta system entirely — rationale: requested by the user ("şimdi meta oyunu implement etmeye başlıycaz"), with the six locked answers gathered before any design (fixed slots; SoftMoney only and price is the only gate; Day-CONTENT-driven required props; Square as an area expansion; locations accumulate rather than replace; a Day number unlocks a location).
